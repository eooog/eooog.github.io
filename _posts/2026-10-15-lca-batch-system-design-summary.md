**Java 21 · Spring Boot 3.4.5 · Spring Batch 5 · Oracle · MyBatis**

여러 원천 시스템의 데이터를 일 단위로 최신화하는 제조업 LCA 배치 시스템이다. DAG 오케스트레이터, 분산 작업 선점 및 재시도, 제품 변경 이력 관리, 대용량 배치 처리 최적화를 직접 구현했다.

| 항목 | 내용 |
| --- | --- |
| 운영 환경 | 복수의 Spring 인스턴스 + 공유 Oracle DB |
| 주요 제약 | 외부 워크플로 엔진 전용 인프라 할당 불가 / 개발 기간 약 2~3주 |
| 처리 규모 | 약 **1,270만 건** (최근 36개월 누적 데이터) |
| 성능 개선 | **51분 → 5분 37초** (처리 시간 약 **89% 단축**) |
| 상세 문서 | [설계 결정 상세 문서]({{ "/posts/lca-batch-system-design-details/" | relative_url }}) |

## 1. 오케스트레이션

### 워크플로 엔진: Flowable 프로토타입 검증 후 자체 구현

Flowable 기반으로 2개 인스턴스·10개 이상의 Task 환경을 구성해 실제 Spring Batch 연동을 테스트했다. 그러나 병렬 실행 가능한 Task가 대기 중임에도 한 인스턴스에 작업이 쏠리고 다른 인스턴스는 유휴 상태로 남는 현상이 나타났다.

| 대안 | 장점 | 단점 |
| --- | --- | --- |
| **Flowable 도입** | DAG 실행, 상태 관리, 재시도 등 워크플로 기능 제공 | 프로토타입에서 작업 분배가 기대대로 동작하지 않아 추가 분석 및 설정 조정 필요 |
| **Spring + Oracle 직접 구현** | 기존 인프라 활용 가능. 필요한 기능만 구현해 일정에 맞춰 개발 가능 | 실행 상태 관리, Lease, 장애 복구 로직을 직접 개발하고 유지보수해야 함 |

**결정:** 별도 엔진 서버를 띄울 수 없는 인프라 제약과 2~3주라는 짧은 일정을 고려해, 엔진 내부를 파고드는 대신 필요한 범위의 코디네이터를 직접 구현했다.

### DAG 정의: YAML + 버전별 Snapshot

- YAML 선언 → **사이클 검증(DAG 여부)** → DB Snapshot과 비교 → 변경 시 신규 반영.
- JobRun은 생성 시점의 **DAG Snapshot을 고정**하여 참조.
- 배포 중 DAG 정의가 바뀌어도 이미 실행 중인 JobRun의 선후행 의존 관계에는 영향 없음.
- 기존 Snapshot과 구조가 동일하면 DB 업데이트 생략.

### 의존성 판정: 목표 / 충족 Indegree 카운터

| 컬럼 | 의미 |
| --- | --- |
| 목표 Indegree | 실행 전 완료되어야 하는 선행 Task 총개수 |
| 충족 Indegree | 현재까지 정상 완료된 선행 Task 개수 |
| READY 전환 조건 | **목표 Indegree = 충족 Indegree** |

```text
A ──┐
    ├──→ C       C: 목표 2 / 충족 0
B ──┘            A 성공 → 충족 1
                 B 성공 → 충족 2 → C READY 전환
```

매 실행마다 Edge별 완료 상태를 별도 레코드로 저장하고 조인 조회하는 대신, **두 카운터 값 비교만으로 READY 전환 여부를 판단**해 비용을 줄였다.

**중복 반영 방지:** 선행 TaskRun의 최초 `RUNNING → SUCCESS` 상태 전이와 후속 TaskRun의 충족 Indegree 증가(`+1`)는 **단일 DB 트랜잭션**으로 묶어 처리한다. 원천 데이터 변경분이 없는 Task도 정상 성공(SUCCESS)으로 처리해 후속 흐름을 이어간다.

### 작업 분배: Master 노드 없는 DB Polling

```text
Instance A ─┐
            ├──→ Oracle DB (READY TaskRun 조회)
Instance B ─┘           │
                        ▼
                 짧은 DB Lock 획득
                 Owner / Lease 기록
                        │
                  Lock 해제·Commit
                        ▼
                  Spring Batch 실행
```

- **로컬 CAS 예약:** 단일 인스턴스 내 Worker가 동시에 하나의 TaskRun만 가져가도록 제어.
- **DB Lock + Owner 기록:** 여러 인스턴스가 동일한 TaskRun을 중복 선점하지 않도록 제어.
- **Lease / Heartbeat:** 실행 중 주기적으로 소유권 만료 시각 갱신. 비정상 종료된 인스턴스의 작업 회수 가능.
- **트랜잭션 분리:** DB Lock은 작업 선점 시점에만 짧게 유지하고 즉시 해제. 수분 이상 걸리는 실제 배치 실행 중에는 Lock을 물고 있지 않음.
- **좀비 작업 방어:** Lease가 만료된 이전 TaskRun이 뒤늦게 성공을 보고하더라도 상태 변경 거부.

## 2. 장애 복구와 데이터 정합성

### 재시도: 새 TaskRun 생성, Spring Batch JobInstance 유지

| 구분 | 실패 시 동작 |
| --- | --- |
| JobRun | 해당 일자(Time Slot)의 전체 워크플로 실행 유지 |
| TaskRun | 기존 기록 보존, **새로운 실행 시도 레코드 생성** |
| Spring Batch JobInstance | 동일한 식별용 JobParameters를 전달해 **기존 인스턴스 유지** |
| Spring Batch JobExecution | 재시도 때마다 하위 실행(Execution)만 새로 생성 |
| ItemReader | 실패 직전 마지막으로 커밋된 Chunk 체크포인트부터 읽기 재개 |

- 최대 재시도 횟수(5회)를 모두 소진하면 해당 JobRun을 최종 `FAILED` 처리하고 후속 DAG 진행을 중단한다.
- Lease 만료 직후 이전 Worker의 배치 스레드가 잠시 겹쳐 돌 수 있으므로, **작업 선점 제어와는 별개로 데이터 레벨에서 중복·역전을 방어**한다.

### 중복 실행 및 구버전 덮어쓰기 방어: Batch ID 버전 가드

| 보호 대상 | 방어 메커니즘 |
| --- | --- |
| 동일 Time Slot의 JobRun 중복 생성 | `UNIQUE(Job ID, Time Slot)` 제약 |
| 현재 제품 테이블 INSERT / UPDATE | 기존 저장된 Batch ID보다 **새 Batch ID가 더 클 때만** 반영 |
| 구버전 제품 물리 DELETE | `저장된 Batch ID < 현재 실행 Batch ID` 조건 적용 |
| 변경 이력 중복 적재 | `UNIQUE(제품 복합키, Batch ID)` 제약 |

동일 일자 재시도 시 원천 데이터는 변하지 않는다. 만약 Lease 만료로 인해 이전 실행과 새 실행의 연산이 일시적으로 겹치더라도, 구버전 작업이 최신 데이터를 덮어쓰거나 지우지 못하도록 쿼리 조건(Batch ID 가드)으로 차단했다.

### 제품 변경 이력: 물리 DELETE 시점 지연

현재 제품 테이블(Source of Truth)과 `I/U/D` 변경 이력 테이블은 역할이 다르므로, **제품 적재 배치와 이력 생성 배치를 별도의 선후행 DAG Task로 분리**했다.

```text
① 선행 적재 배치: 현재 제품 INSERT / UPDATE (신규 Batch ID 기록)
   └─ 이번 원천에서 빠진 제품은 이전 Batch ID를 가진 채로 유지
                     ↓
② 후행 이력 배치
   ├─ 신규 제품(I) / 값 변경 제품(U) 이력 생성
   └─ 이전 Batch ID로 남아 있는 제품(삭제 대상)에서 삭제(D) 이력 생성
                     ↓
③ 정리 작업: D 이력 기록 완료 후 구버전 제품 물리 DELETE
```

| 설계 선택 | 근거 및 효과 |
| --- | --- |
| **이력 기록 후 물리 DELETE** | 삭제 대상을 추적하기 위한 별도 임시 테이블이나 백업 과정이 필요 없음 |
| 제품 복합키 인덱스로 최신 이력 조회 | 수천만 건 이상의 전체 이력 테이블 풀 스캔 방지 |
| 변경 없는 제품은 이력 생략 | `I/U/D` 테이블에 실제 상태 변화 이벤트만 기록 |
| 삭제(D) 후 재등장 시 신규(I) 기록 | 제품의 재등장을 새로운 생성 라이프사이클로 명확히 표현 |

**트레이드오프:** 선행 적재 후 물리 삭제가 완료되기 전까지 삭제 예정 제품이 현재 테이블에서 잠시 조회될 수 있다. 배치가 현업 출근 전인 새벽 시간대에 완료되는 운영 특성을 고려해 복잡도를 낮추는 쪽을 택했다.

### 지나간 날짜의 배치는 다시 실행하지 않음

원천 시스템의 데이터는 일 단위로 갱신되며 과거 일자의 스냅샷을 역산해 제공하지 않는다. 따라서 스케줄러는 **당일(현재 Time Slot) 실행만 처리**하며, 지나간 날짜의 배치를 자동으로 다시 실행하지 않는다.

## 3. 대용량 배치 처리와 성능 최적화

### Partitioning: 비즈니스 로직 변경 경계 우선 분리

- **처리 대상:** 최근 **36개월 치** 누적 데이터 (약 1,270만 건).
- **도메인 특성:** 2025년 전후를 기점으로 **참조 원천 테이블과 배출량 산정 SQL이 달라짐**.
- **분할 전략:** 36개월을 단순 N등분하지 않고, 먼저 원천·산정 로직이 바뀌는 경계로 구간을 나눈 뒤 각 구간을 다시 연속된 연월 범위로 쪼개 병렬 실행.
- **정적 분할 선택:** 최근 5년 치 월별 데이터 건수를 분석한 결과 월별 편차가 크지 않아, 구조가 단순한 **정적 기간 분할**로 충분하다고 판단.
- **ItemReader:** 복잡한 다중 조인 쿼리 특성상 OFFSET Paging의 후반부 스캔 비용 증가와 Keyset 구성의 한계를 피하기 위해, **커스텀 MyBatis Cursor ItemReader**를 구현하여 스트리밍 방식으로 읽고 체크포인트 재시작 연동.

### DB 접근 최적화: 건별 SELECT → Chunk 단위 일괄 선조회 (Pre-fetching)

```text
[Before: 건별 단건 조회]
Item 1 → DB SELECT → 비교
Item 2 → DB SELECT → 비교
Item 3 → DB SELECT → 비교 ... (N번의 DB 왕복 발생)

[After: Chunk 단위 일괄 조회]
Chunk 내 제품 복합키 수집
     ↓
IN 절을 활용해 기존 데이터 1회 일괄 조회
     ↓
Worker Thread별 로컬 Map/Cache 적재
     ↓
메모리에서 비교 후 INSERT / UPDATE / SKIP 분류
     ↓
Chunk 단위 Bulk Write
```

**핵심 개선:** 멀티스레딩 적용 후에도 남아 있던 단건 조회(N+1) I/O 병목을 **Chunk 단위 집합 조회와 스레드 로컬 캐시 비교**로 전환해 제거했다. 캐시는 매 Chunk가 끝날 때마다 비우고 새로 채운다.

### 성능 개선 결과

| 단계 | 소요 시간 | 직전 단계 대비 |
| --- | ---: | ---: |
| 초기 구현 (단일 스레드 + 건별 조회) | **51분** | — |
| 1차: 연월 Partition 병렬 실행 | **약 12분 30초** | 약 75.5% 단축 |
| 2차: Chunk 단위 일괄 선조회·캐시 적용 | **5분 37초** | 약 55.1% 추가 단축 |

**최종 성과: 약 1,270만 건 처리 시간 약 89% 단축 (51분 → 5분 37초).**

적정 Worker 스레드 수는 CPU 코어 수를 기준으로 시작해, Prometheus에서 애플리케이션 CPU 사용률과 전체 배치 소요 시간을 확인하며 결정했다.
