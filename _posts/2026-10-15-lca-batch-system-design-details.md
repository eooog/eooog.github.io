# 설계 결정으로 살펴보는 LCA 배치 시스템

**Backend Engineering · Selected Design Decisions**  
Java 21 · Spring Boot 3.4.5 · Spring Batch 5 · Oracle · MyBatis

## 프로젝트 개요

제조업 LCA 플랫폼에서 여러 원천 시스템의 데이터를 일 단위로 최신화하는 배치 시스템을 구축했다. 작업 간 선후행 관계를 관리하는 오케스트레이터를 새로 개발해야 했고, 일부 배치는 수천만 건에 달하는 누적 데이터를 처리해야 했다. 이 프로젝트에서 DAG 기반 실행 스케줄링, 분산 환경의 작업 점유 및 복구, 제품 데이터 및 변경 이력 최신화, 대용량 배치 병렬 처리와 DB 조회 최적화를 직접 수행했다.

인프라와 일정상의 제약도 고려해야 했다. 고객사 환경 특성상 별도의 워크플로 엔진을 띄울 독립 자원을 할당받기 어려웠고, 오케스트레이터 구현에 주어진 시간도 약 2~3주뿐이었다. 반면 여러 대의 Spring 인스턴스와 공유 Oracle DB는 바로 활용할 수 있었기 때문에, 외부 워크플로 엔진을 도입하는 대신 기존 Spring 애플리케이션과 Oracle DB만으로 DAG 실행 제어와 장애 복구 기능을 직접 구현했다.

이 문서는 단순한 기능 나열 대신, 시스템을 구축하며 내린 주요 설계 결정과 그 근거를 다룬다.

## 결정 1. 외부 워크플로 엔진 도입 vs 직접 구현

### 해결해야 했던 문제

10개 이상의 Task가 의존 관계를 맺고 있는 배치를 여러 애플리케이션 인스턴스에서 분산 실행해야 했다. 선후행 관계가 없는 독립적인 Task는 동시에 실행되어야 했고, 선행 Task의 성공 여부나 복구 상태에 따라 후속 Task의 실행 여부가 결정되어야 했다.

처음부터 자체 구현을 택한 것은 아니며, 우선 오픈소스 엔진인 Flowable 도입을 검토했다. 공식 문서와 예제를 바탕으로 두 대의 Spring 인스턴스가 하나의 DB를 공유하는 환경을 구성하고, 실제 Spring Batch 잡을 호출하는 DAG 프로토타입을 만들어 테스트했다.

하지만 프로토타입 테스트에서 작업이 의도대로 분배되지 않는 현상이 나타났다. 실행 조건이 충족된 대기 중인 Task가 남아 있는데도, 한 인스턴스가 무거운 배치를 돌리는 동안 다른 유휴 인스턴스가 남은 작업을 가져가지 않았다. 심지어 긴 작업이 끝난 뒤에야 기존 인스턴스가 대기 중이던 나머지 Task까지 연달아 가져가 실행했다. 즉, 당시 구성만으로는 **유휴 인스턴스가 병렬 처리 가능한 작업을 적시에 가져가는 동작을 보장할 수 없었다.**

### 선택과 이유

Flowable의 내부 실행 모델과 스레드 풀 설정을 깊이 파고들어 튜닝하는 대신, Spring과 Oracle DB를 활용해 필요한 기능만 갖춘 경량 코디네이터를 직접 구현하기로 했다.

Flowable 자체의 한계라기보다는 주어진 인프라 환경과 2~3주라는 짧은 개발 기간, 그리고 엔진 내부 동작을 분석하는 데 드는 학습 비용을 현실적으로 저울질한 결과였다. 별도 엔진 서버를 구축할 수 없는 상황에서 범용 워크플로 기능을 고집하기보다, **우리에게 꼭 필요한 DAG 실행, 작업 점유, 재시도 로직만 기존 Spring과 Oracle DB 위에 빠르게 구축하는 편**이 낫다고 판단했다.

물론 직접 구현하면 유지보수 부담이 생긴다. 이를 최소화하기 위해 그래프 정의, 실행 상태 관리, 작업 소유권 제어, 그리고 실제 데이터 처리(Spring Batch)의 책임을 명확히 분리하는 데 집중했다.

## 결정 2. DAG의 실행 가능 여부를 어떻게 판단할 것인가?

### 불변인 그래프 정의와 변하는 실행 상태의 분리

DAG 구조는 애플리케이션 YAML에 정의했다. 인스턴스가 기동할 때 그래프에 사이클이 없는지(DAG 여부) 검증하고, DB에 저장된 기존 Snapshot과 비교해 변경 사항이 없으면 업데이트를 건너뛰었다. 그래프 정의가 바뀌면 새 Snapshot을 생성하되, **이미 실행이 시작된 JobRun은 시작 시점의 Snapshot을 그대로 참조**하도록 설계했다.

이렇게 함으로써 배포 중 그래프 정의가 변경되더라도 이미 돌고 있는 배치의 의존성 판단에는 영향이 없도록 격리했다.

하나의 JobRun이 시작되어 하위 TaskRun들을 생성할 때, 각 TaskRun 레코드에는 다음 두 값을 기록한다.

- **목표 Indegree:** 실행되기 위해 완료되어야 하는 선행 Task의 총개수
- **충족 Indegree:** 현재까지 정상 완료된 선행 Task의 개수

예를 들어 선행 Task가 2개인 작업 B는 목표 2, 충족 0인 상태로 생성된다. 이후 선행 Task들이 성공할 때마다 충족 카운터를 1씩 올리고, **목표치와 충족치가 같아지는 순간 작업 B의 상태를 READY로 전환**한다.

### 실행 때마다 선행 Task 상태를 다시 조회하지 않은 이유

매번 후속 Task의 실행 가능 여부를 판단할 때마다 Edge 테이블을 조인해 선행 Task들의 완료 여부를 조회하는 방법도 있다. 하지만 한 번 시작된 JobRun이 참조하는 DAG Snapshot은 절대 변하지 않는다. 따라서 매번 그래프 관계를 다시 탐색할 필요 없이, **고정된 목표 카운트와 현재 완료 카운트 두 숫자만 비교**하는 것으로 충분하다고 판단했다. 

Edge 단위의 완료 상태를 별도로 저장하고 매번 조인해서 확인하는 비용을 없애고, 상태 전이 로직을 단순화하기 위한 선택이었다.

이 카운터 방식이 정확하게 동작하려면 선행 작업의 완료 이벤트가 중복으로 반영되지 않아야 한다. 이를 보장하기 위해 선행 TaskRun의 **상태 변경(`RUNNING → SUCCESS`)과 후속 TaskRun의 충족 카운터 증가(`+1`)를 하나의 DB 트랜잭션으로 묶어 처리**했다. 또한 원천 데이터에 변경분이 없어 실제 Write가 발생하지 않은 작업도 정상 성공으로 간주해 후속 작업이 막히지 않도록 했다.

## 결정 3. Master 노드 없이 여러 인스턴스가 어떻게 작업을 분배할 것인가?

### 작업 점유와 실제 배치 실행의 트랜잭션 분리

별도의 Master 노드를 두지 않는 대칭형 구조를 택했다. 각 Spring 인스턴스가 공유 DB에서 `READY` 상태인 TaskRun을 주기적으로 Polling하며, 여유가 있는 인스턴스가 작업을 선점해 실행한다.

작업 선점 과정에는 두 단계의 락/상태 제어를 두었다.

1. **인스턴스 내부 Worker Context (로컬 제어):** 인스턴스 내부에서 현재 실행 중인 TaskRun ID를 CAS(Compare-And-Swap)로 먼저 예약한다. 단일 인스턴스가 동시에 여러 Task를 중복해서 가져가지 못하게 막는 장치다.
2. **공유 DB의 TaskRun 상태 (분산 제어):** 짧은 DB 비관적 락(또는 조건부 UPDATE)을 통해 TaskRun의 실행 상태, Owner 인스턴스, Lease 만료 시각을 갱신하여 인스턴스 간 중복 선점을 방지한다.

만약 DB 선점에 실패하면 로컬 CAS 예약도 즉시 해제한다. 작업 선점에 성공하면 즉시 DB 트랜잭션을 커밋해 락을 풀고, 실제 무거운 배치 작업을 시작한다. 배치가 도는 동안에는 주기적으로 Lease 만료 시각을 연장(Heartbeat)한다.

**작업 선점과 실제 배치 실행의 트랜잭션을 분리한 이유**는 두 작업의 소요 시간 차이가 크기 때문이다. 선점은 밀리초 단위로 끝나지만 실제 배치는 수분 이상 걸린다. 배치 실행 내내 DB 락을 물고 있으면 다른 인스턴스의 스케줄링과 상태 갱신까지 병목이 생길 수밖에 없다.

### Lease 만료와 좀비 작업 방어

인스턴스가 비정상 종료되어 Lease가 만료되면, 새로운 TaskRun을 생성해 다른 인스턴스에서 재시도할 수 있다. 이때 네트워크 지연 등으로 살아남은 이전 인스턴스가 뒤늦게 작업 완료를 보고하더라도, **이미 Lease가 만료된 TaskRun의 상태 변경 요청은 거부**된다. 이를 통해 좀비 작업의 뒤늦은 성공 처리가 DAG의 충족 카운터를 중복으로 올리는 문제를 막았다.

물론 **Lease가 만료되었다고 해서 이전 인스턴스에서 이미 돌고 있던 데이터 처리 스레드가 즉시 강제 종료되는 것은 아니다.** 일시적으로 두 인스턴스에서 같은 배치 연산이 겹칠 수 있는 문제는 뒤에서 설명할 'Batch ID 버전 가드'와 '일별 원천 데이터의 멱등성'을 통해 데이터 레벨에서 방어했다. 일부 긴 작업의 경우 Chunk 커밋 시점마다 Lease를 함께 갱신하는 방식을 병행했다.

## 결정 4. 오케스트레이터의 재시도와 Spring Batch의 재시작을 어떻게 연동할 것인가?

TaskRun 실행이 실패하면 기존 레코드의 상태를 덮어쓰지 않고 **새로운 TaskRun 레코드를 생성**해 재시도 이력을 남긴다. 재시도는 최대 5회까지 허용하며, 그 안에 성공하면 기존 JobRun의 DAG 흐름을 이어서 진행한다. 5회 모두 실패하면 해당 일자의 JobRun 전체를 최종 실패 처리한다.

이때 오케스트레이터에서 새 TaskRun을 만들었다고 해서, 하위 Spring Batch의 `JobInstance`까지 새로 생성하지는 않았다. 각 개념의 역할은 다음과 같이 나눴다.

- **JobRun:** 특정 일자(Time Slot)에 실행되는 전체 DAG 워크플로 단위
- **TaskRun:** 오케스트레이터가 관리하는 개별 노드의 실행 시도 단위
- **Spring Batch JobInstance:** 날짜 등 식별 파라미터(JobParameters)로 구분되는 논리적 배치 단위
- **Spring Batch JobExecution:** 하나의 JobInstance 내에서 발생하는 실제 실행 시도 단위

재시도를 위해 새 TaskRun을 실행할 때, Spring Batch에는 **이전 시도와 동일한 식별용 JobParameters**를 그대로 넘기고 ItemReader의 상태 저장(`saveState`) 옵션을 켰다. 덕분에 배치가 실패 후 재실행되더라도 기존 `JobInstance` 아래에 새로운 `JobExecution`이 생성되면서, **실패 직전 마지막으로 커밋된 Chunk 이후 지점부터 이어서 읽기를 재개**할 수 있었다.

오케스트레이터는 재시도 횟수 제어와 DAG 의존성 진행에만 집중하고, **대용량 데이터를 어디까지 읽었는지 추적하는 체크포인트 관리는 Spring Batch의 기본 메커니즘에 위임**하여 역할을 깔끔하게 분리했다.

## 결정 5. 삭제 이력을 남기기 위해 왜 물리 삭제(Hard Delete)를 뒤로 미뤘는가?

### 현재 테이블과 이력 테이블의 역할

현재 제품 테이블은 제품의 최신 상태를 담고 있는 **Source of Truth** 역할을 한다. 반면 별도의 이력 테이블은 제품의 신규 추가(I), 속성 변경(U), 삭제(D) 이벤트를 시계열로 기록한다.

제품 데이터 적재와 변경 이력 생성은 하나의 배치에서 동시에 처리하지 않고, **DAG 상의 선후행 배치로 분리**했다. 후행 이력 배치는 제품 복합키 인덱스를 타서 직전 최신 이력을 조회한 뒤 현재 제품 테이블의 값과 비교한다. 이전 이력이 없으면 `I`, 값이 달랐으면 `U`를 남기고, 값이 같으면 아무 이력도 남기지 않는다. 한 번 `D` 이력이 남은 제품이 추후 다시 등장하면 새로 `I` 이력을 남긴다.

### 물리 삭제 시점의 결정

만약 선행 적재 배치에서 이번 회차에 사라진 제품을 곧바로 물리 삭제(DELETE)해 버리면, 뒤이어 실행되는 이력 배치에서는 **어떤 제품이 삭제되었는지 알 수 있는 방법**이 사라진다. 이를 알아내기 위해 수천만~수억 건에 달하는 이력 테이블 전체를 역으로 풀 스캔하는 것은 비효율적이고, 삭제 대상을 별도의 임시 테이블에 백업해 두는 방식도 추가적인 I/O와 관리 비용을 발생시킨다.

그래서 삭제된 제품을 즉시 지우지 않고 **현재 제품 테이블에 잠시 남겨 두는 방식**을 택했다.

    ① 선행 적재 배치: 이번 회차 제품 INSERT / UPDATE (신규 Batch ID 부여)
       └─ 이번 원천에서 빠져 갱신되지 않은 제품은 이전 Batch ID를 가진 채로 남아 있음
                     ↓
    ② 후행 이력 배치
       ├─ 최신 Batch ID를 가진 제품: 직전 이력과 비교해 I / U 이력 생성
       └─ 이전 Batch ID를 가진 제품(삭제 대상): D 이력 생성
                     ↓
    ③ 정리 작업: D 이력 기록이 끝난 구버전(이전 Batch ID) 제품들을 물리 DELETE

이 과정에서 동시성 문제나 이전 작업의 지연으로 인해 최신 데이터가 덮어써지는 것을 막기 위해, 모든 INSERT/UPDATE는 기존에 저장된 Batch ID보다 새로운 Batch ID가 더 클 때만 반영되도록 버전 가드를 두었다. 마지막 물리 DELETE 역시 현재 Batch ID보다 작은 레코드만 지우도록 조건을 걸었고, 이력 테이블에는 `(제품 복합키 + Batch ID)` Unique 제약을 걸어 재시도 시에도 중복 이력이 쌓이지 않게 막았다.

### 트레이드오프

별도의 삭제 후보 테이블을 만들지 않아 구조가 단순해진 대신, **선행 적재가 끝나고 후행 이력 배치가 물리 삭제를 마칠 때까지의 짧은 시간 동안에는 이미 삭제된 과거 제품이 현재 테이블에 남아 있게 된다.** 

이 배치는 현업 담당자들이 출근하기 전인 새벽 시간대에 완료되도록 스케줄링되어 있었기 때문에, 배치 도중의 일시적인 노출은 실무에 영향이 없다고 판단해 이 방식을 채택했다. 실시간 무중단 정합성을 위해 복잡한 스테이징 테이블이나 뷰 스위칭을 도입하는 대신, **운영 시간대라는 도메인 특성과 순차적인 파이프라인 흐름을 활용해 복잡도를 낮춘 결정**이었다.

---

## 결정 6. 데이터 특성에 맞춰 병렬 처리를 어떻게 구성할 것인가?

### 균등 분할에 앞서 비즈니스 로직이 바뀌는 경계부터 분리

처리 대상인 대용량 테이블은 시간순으로 데이터가 쌓이는 구조였고, 한 번에 처리해야 하는 범위는 **36개월 치(약 1,270만 건)**였다. 그런데 도메인 특성상 **2025년 전후를 기점으로 참조해야 하는 원천 테이블 구조와 배출량 산정 SQL이 완전히 달랐다.**

따라서 36개월을 단순히 스레드 개수만큼 N등분하지 않고, **먼저 원천 테이블과 산정 로직이 달라지는 시점을 기준으로 크게 구간을 나눈 뒤**, 각 구간 내부를 다시 연속된 연월 범위(Partition)로 쪼개어 Worker 스레드에 할당했다.

파티션을 나눌 때 1개월 단위로 36개의 잘게 쪼갠 파티션을 만들고 스레드 풀에서 동적으로 가져가게 하는 방법도 고려했다. 하지만 사전 조사에서 최근 5년 치 데이터의 월별 적재량을 확인해 본 결과, 월별 건수 편차가 크지 않고 고르게 분포되어 있었다. 데이터가 균등한 상황에서 굳이 파티션을 잘게 쪼개 동적 분배 오버헤드를 감수할 이유가 없었으므로, **파티션 구성을 단순하게 유지할 수 있는 정적 기간 분할**을 선택했다.

### Paging 대신 Cursor Reader를 선택한 이유

원천 데이터는 여러 테이블을 복잡하게 조인하고 집계한 결과였다. 일반적인 `OFFSET` 기반 Paging을 쓰면 뒤쪽 페이지로 갈수록 앞선 데이터를 버리는 스캔 비용이 증가하고, 그렇다고 `Keyset(No-Offset)` Paging을 쓰기에는 복잡한 조인 쿼리 특성상 고유하고 정렬 가능한 단일 인덱스 키를 잡기가 까다로웠다.

이를 해결하기 위해 커스텀 **MyBatis Cursor ItemReader**를 구현했다. 각 파티션이 담당하는 연월 범위를 파라미터로 넘겨 DB 커서를 열고 스트리밍 방식으로 데이터를 읽어 들이되, Spring Batch의 체크포인트 메커니즘과 연동해 중간 실패 시에도 마지막으로 커밋된 Chunk의 읽기 위치부터 재처리할 수 있도록 구성했다.

## 결정 7. 멀티스레딩 적용 후, 왜 추가로 Chunk 단위 DB 조회를 최적화했는가?

### 진짜 병목은 연산이 아닌 건별 DB 왕복(N+1) 비용

제품 데이터 적재는 읽어온 데이터를 그대로 밀어 넣는 단순 작업이 아니었다. 기존에 이미 등록된 제품인지, 기존 값과 비교해 실제로 변경된 속성이 있는지 먼저 확인해야 했고, 초기 구현에서는 이를 확인하기 위해 ItemProcessor에서 레코드 건마다 DB에 SELECT 쿼리를 날렸다.

먼저 결정 6의 연월 파티션 병렬 처리를 적용해 전체 시간을 51분에서 12분 30초로 줄였다. 하지만 스레드 수를 더 늘려도 성능은 더 이상 개선되지 않았다. 스레드가 많아져도 결국 각 스레드가 매 레코드마다 DB를 찌르는 구조(건별 조회)가 그대로여서 DB I/O와 네트워크 왕복 비용이 병목으로 작용했기 때문이다.

이를 해결하기 위해 **Chunk 단위로 비교 대상 제품의 복합키들을 모은 뒤, `IN` 절을 활용해 한 번에 일괄 조회(Pre-fetching)**하도록 구조를 바꿨다. 일괄 조회한 기존 데이터는 **각 Worker 스레드 내부의 로컬 캐시(Map)**에 올려두고, 개별 레코드 비교는 DB 접근 없이 메모리에서 처리했다. 해당 Chunk 처리가 끝나면 캐시를 비우고 다음 Chunk를 위해 새로 로딩했다.

    기존: 제품 1건 읽기 → DB 단건 조회 → 비교 → 다음 제품 1건 읽기 → DB 단건 조회 ... (Chunk 크기만큼 반복)
    개선: Chunk 단위 제품 키 수집 → DB 일괄 조회(1회) → 스레드 로컬 캐시 적재 → 메모리 내 고속 비교

메모리 비교를 통해 `INSERT`, `UPDATE`, `SKIP(변경 없음)` 대상을 분류한 뒤, 최종적으로 변경이 필요한 건들만 모아서 Chunk 단위 Bulk Write로 밀어 넣었다. 핵심은 **레코드 건별로 발생하던 수천만 번의 DB 조회를 Chunk 단위의 집합 조회로 바꾼 것**이다.

### 측정 기반의 스레드 수 튜닝

적정 스레드 수는 임의의 공식에 의존하지 않고 실제 모니터링 지표를 보며 결정했다. 코어 수를 기준으로 초기값을 잡은 뒤, **Prometheus에서 애플리케이션 CPU 사용률을 확인하고 전체 배치 소요 시간을 비교**하며 스레드 수를 단계적으로 조정했고, 처리 시간이 수렴하는 최적 지점을 찾아 반영했다.

### 단계별 성능 개선 결과

동일한 운영 환경에서 약 **1,270만 건**의 데이터를 처리한 실측 결과다.

| 최적화 단계 | 소요 시간 | 직전 단계 대비 |
| --- | ---: | ---: |
| 초기 구현 (단일 스레드 + 건별 조회) | **51분** | — |
| 1차: 연월 파티션 기반 병렬 처리 적용 | **약 12분 30초** | 약 75.5% 단축 |
| 2차: Chunk 단위 일괄 선조회 및 로컬 캐시 적용 | **5분 37초** | 약 55.1% 추가 단축 |

최종적으로 **전체 배치 처리 시간을 약 89%(51분 → 5분 37초) 단축**했다. 단순히 스레드 수만 늘려서 얻은 결과가 아니라, **도메인 특성에 맞춘 파티션 분할과 DB 접근 패턴(건별 → 집합 조회) 개선을 순차적으로 결합해 병목을 제거한 결과**다.

## 설계상 타협한 지점과 한계 (Trade-offs)

주어진 제약 조건 안에서 시스템을 설계하며 의도적으로 타협한 경계들은 다음과 같다.

- **전역적인 Exactly-once 실행을 보장하지는 않는다:** 네트워크 단절 등으로 Lease가 만료될 때 일시적으로 이전 Worker와 새 Worker의 배치 연산이 겹칠 수 있다. 대신 애플리케이션 레벨의 강제 종료를 구현하는 대신, 데이터의 `Batch ID` 버전 가드와 일별 원천 데이터의 멱등성을 활용해 최종 데이터 정합성을 지키는 방향을 택했다.
- **지나간 날짜의 배치는 다시 실행하지 않는다:** 스케줄러는 당일(현재 Time Slot) 실행만 다루며, 장애 등으로 특정 일자를 통째로 건너뛴 경우 과거 시점의 스냅샷을 다시 가져와 처리하지 않는다.
- **배치 실행 중 일시적인 중간 상태 노출을 허용한다:** 삭제 이력을 남기기 위해 물리 삭제를 후행 배치 뒤로 미뤘기 때문에, 두 배치 사이의 짧은 시간 동안 삭제 대상 제품이 조회될 수 있다. 새벽 배치 시간대라는 운영 특성을 고려해 수용한 비용이다.
- **장애 복구와 완료 알림은 분리되어 있다:** 알림 발송(Notification)이 실패하더라도 이미 완료된 JobRun의 상태가 롤백되지는 않는다.

## 마무리

이 프로젝트의 핵심은 **책임의 분리**와 **병목 지점의 정확한 타격**이었다. 

변하지 않는 DAG 정의와 매번 변하는 실행 상태(Indegree 카운터), 가벼운 작업 선점 트랜잭션과 무거운 배치 실행, 오케스트레이터의 워크플로 재시도와 Spring Batch의 데이터 읽기 체크포인트, 그리고 제품의 현재 상태와 변경 이력 생성의 책임을 각각 분리해 외부 엔진 없이도 안정적인 분산 배치 시스템을 구축할 수 있었다. 

성능 면에서도 무작정 자원을 늘리기보다 파티션 분할로 작업 단위를 나눈 뒤, 실제 병목이었던 단건 DB 조회를 Chunk 단위 일괄 조회로 개선함으로써 51분 걸리던 대용량 배치를 5분 37초까지 단축할 수 있었다.
